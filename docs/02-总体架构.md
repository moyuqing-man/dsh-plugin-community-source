## 2. 「双形态交付」是本方案的核心架构决策

### 2.1 问题

DSH 的 client 插件是**运行时注入**的：`clientModules` 服务在页面加载时把插件的 client bundle 注入 `__DSH_BOOT__` entries。

而手机方案 `dsh-phone-pair` 的前端是**构建时快照**——它是从使用者电脑的 DSH Web GUI 抓下来的静态文件（约 28 MB / 85 个内容哈希资源）。

**两者大概率对不上。** 后果就是「插件 UI 不显示」。

更糟的是，这个失败**是静默的**：页面上什么都没有，用户以为插件没装。唯一的判据是页面 HTML 字节数（34846 = 正常，3709 = 插件图为空）。

### 2.2 对策

**社区页不把宝押在 slot 注入上。** 同一份数据、同一套视觉，提供三条互相独立的路：

| 形态 | 实现 | 依赖 | 谁用 |
|---|---|---|---|
| ① slot 注入 | `ctx.slots.register(...)` | client 插件图必须正常 | 桌面 DSH、`dsh-android` |
| ② 独立页面 | `ctx.webServer.register({ kind:'exact', path:'/community' })` 返回整页 HTML | **只依赖 host 的 HTTP 服务** | 任何浏览器、任意 WebView、`dsh-phone-pair` |
| ③ JSON API | `ctx.webServer.register({ path:'/api/v1/community/*' })` | 只依赖 host | 原生客户端、第三方集成 |
| ④ Agent 工具 | `ctx.tools.register(defineTool({...}))` | 只依赖 host | 任何 DSH 会话（让 Agent 替你查社区） |

**关键性质：②③④ 全部不依赖 client 插件图。** 只要 DSH 进程活着、Web 服务在跑，社区就能用。

> 这是对用户「**不能就我们主动兼容**」这句话的工程回答：与其求手机端 App 改架构，不如让社区页**根本不需要插件的 client 半边**。

### 2.3 形态②的可行性依据

DSH 的 `webServer` 服务提供 `register(route)`，`dsh-workspace` 插件就是用它注册了 10 个 `/api/v1/dsh-workspace/*` 路由，形态如下（实测源码）：

```js
ctx.effect(() => webServer.register({
    kind: 'exact', path: '/api/v1/dsh-workspace/summary',
    async handler(req, res) { /* 原生 Node http req/res */ },
}));
```

`handler` 拿到的是**原生 Node 的 `req`/`res`**，所以形态②可以自由 `res.end(html)` 返回一整个页面。这条路完全成立。

## 3. 分层职责

### L1 · 桥接层（host 半边）

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `sources/` | 把每个索引源适配成统一的 `PluginCard` | 每个源一个 adapter，可独立失效；**只读**，绝不写回 |
| `sources/registry` | 源优先级与去重合并 | 按 `owner/repo` 归一化；字段冲突时按源的 `trust` 权重取 |
| `github/rest` | **所有的读**：repo 元数据、releases、commits、**讨论列表 / 讨论详情 / 评论**、search | 未认证 **60/h 且按来源 IP**（NAT 后多人共享）、认证 5000/h；`search` 另限 **10/分钟**；把 `x-ratelimit-remaining` / `x-ratelimit-reset` 当**一等公民** |
| `github/graphql` | **只有两件事**：① 写（`createDiscussion` / `addDiscussionComment` / reaction）② 取 `discussionCategories`。✅ POC-2 实测：REST 侧**没有** discussions 写接口 | 未认证配额实测为 **0** → **未登录时完全不碰 GraphQL**；建帖必须带 `categoryId`，而分类只能从这里取 |
| `identity/` | Device Flow 全流程 | token 交给 `ctx.credentials`，**插件自己不落盘** |
| `cache/` | 分层 TTL 缓存 | 走 `ctx.storage`，避免重复打 GitHub |
| `http/pages` | 形态②：服务端渲染的独立页面 | **不能用任何构建期工具链**，直接输出 HTML 字符串 |
| `http/api` | 形态③：JSON API | 统一错误信封 `{status, reason, message, fields, requestId}`（对齐 `dsh-workspace` 的风格） |
| `tools/` | 形态④：Agent 工具 | 让 Agent 能查/发帖，需登录态 |

### L2 · 界面层（client 半边）

| 模块 | 职责 |
|---|---|
| `pages/` | 社区首页、插件详情、帖子详情、发帖、搜索、需求板 |
| `slots/` | 往官方槽位挂入口（见 [05](05-界面与交互设计.md)） |
| `client/api` | 调 `/api/v1/community/*`，统一走 DSH 的 `connection` |
| `theme/` | 只用 DSH 的 `--dsw-*` 主题变量，跟随主题切换 |

**L1 与 L2 的关系**：L2 **只**通过 HTTP API 访问 L1。不共享内存、不直接 import host 模块。这样形态②可以直接复用形态①的数据契约，也让 L2 在独立页面场景下可以退化。

## 4. 数据流

### 4.1 读路径（插件详情页）

```
用户打开插件详情
    │
    ▼
client 形态① ──┐
独立页面 形态② ──┼──► GET /api/v1/community/plugin?repo=owner/name
JSON API  形态③ ──┘
    │
    ▼
L1 cache 命中？
    ├─ 是 → 直接返回
    └─ 否 → ┬─ sources/*  取索引元数据（名称、描述、版本、作者）
            ├─ github/rest  取 repo 元数据（stars、open issues、pushed_at、archived）
            └─ github/rest   取 Discussions 关联帖 + 评论（免登录，见 [08](08-GitHub-API-契约.md)）
                 │
                 ▼
            合并为 PluginCard → 写 cache → 返回
```

### 4.2 写路径（发帖 / 评论）

```
用户点「发帖」
    │
    ▼
L2 检查登录态（GET /api/v1/community/me）
    ├─ 未登录 → 弹 Device Flow 引导（见 04）
    └─ 已登录 → 显示编辑器
         │
         ▼
POST /api/v1/community/discussion
    │
    ▼
L1: ctx.credentials.resolve('community:github') → token
    │
    ▼
github/graphql: createDiscussion mutation
    │
    ▼
成功 → 清相关 cache → 返回新帖 URL
```

### 4.3 缓存策略（关键：GitHub rate limit 是硬约束）

**实测硬数字**（[08](08-GitHub-API-契约.md) 第 2 节）：未认证 **60 次/小时，且按来源 IP**；`search` 端点另限 **10/分钟**；认证后 5000/小时。

> **「按 IP」而不是「按用户」**——公司、学校、家庭 NAT 后面多个用户会共用这 60 次。
> 所以缓存**不是优化项，是必需品**。

| 数据 | TTL | 理由 |
|---|---|---|
| 插件索引（多源） | 6h | 与 `DSH-Plugins-Marketplace` 的 2h CI 刷新同量级，但社区不需要那么新 |
| repo 元数据（stars / issues） | 1h | 变化慢，但用户期望「不太旧」 |
| Discussions 列表 | 10–15min | 活跃度较高 |
| 单个帖子内容 + 评论 | 3–5min | 用户发帖后要看到自己的帖子 |
| 登录用户信息 | 24h | 几乎不变 |
| **npm 周下载量** | 6–24h | 变化极慢，且**不吃 GitHub 配额**（`api.npmjs.org`） |
| **讨论分类 ID** | 24h | 登录后取一次，几乎不变 |
| 搜索建议 | 30min | 可接受短时陈旧 |

**配额调速器（Quota Governor）**——比 TTL 更重要的一层：

每次响应都读 `x-ratelimit-remaining` / `x-ratelimit-reset` 并写进缓存元数据；当 `remaining` 低于阈值（建议 10）时：

1. **自动延长所有 TTL**，停止后台预取
2. 优先保证「用户主动点开的页面」有配额可用，后台刷新一律让路
3. 在界面上明确提示数据可能较旧（而不是假装数据是新的）

**降级原则**：任何一次外部请求失败，都返回**缓存中的陈旧数据 + `stale: true` 标记**，而不是报错。社区页宁可显示 6 小时前的数据，也不能白屏。

**已实测（POC-6，结论与预期相反）**：304 / ETag **会计入配额**（`x-ratelimit-remaining` 差值 = 1，3/3 次复现）。条件请求只**省带宽、不省配额**，因此**不能用它来提高轮询频率**。配额门控改为依赖**免费的 `/rate_limit` 探针**（实测该端点自身不消耗配额）。详见 [08](08-GitHub-API-契约.md) §9.2。

## 5. 身份与安全

- token 存在 DSH 自带的 `ctx.credentials`，**插件自己绝不落盘、绝不打印**。
- 前端**永远拿不到 token**：所有 GitHub 调用在 host 侧完成，L2 只面对 `/api/v1/community/*`。
- 独立页面（形态②）与 JSON API（形态③）默认**仅允许本机访问**，对齐 `dsh-workspace` 的 `isLoopback(req)` 检查；远程访问需显式配置开关。
- 所有写操作在 host 侧二次校验登录态，不信任前端。
- 错误信息中不出现 token、不出现服务器绝对路径。

## 6. 工程量估算

| 模块 | 规模 | 说明 |
|---|---|---|
| `sources/` 多源适配 | ~600 行 | 6 个源，每个 100 行左右；可先做 2 个 |
| `github/` REST + GraphQL | ~500 行 | 查询封装、分页、限流退避 |
| `identity/` Device Flow | ~200 行 | 流程短，逻辑清晰 |
| `cache/` | ~150 行 | 分层 TTL，可先做内存版 |
| `http/pages` 独立页面 | ~800 行 | SSR 字符串模板 + 少量内联 JS/CSS |
| `http/api` | ~300 行 | 路由分发 + 错误信封 |
| `tools/` Agent 工具 | ~300 行 | 3–4 个工具 |
| `pages/` client UI | ~1500 行 | 6 个页面，复用 DSH 主题变量 |
| `slots/` 挂载 | ~150 行 | 4–5 个槽位 |
| **合计** | **约 4500 行** | 不含测试与文档 |

**零原生依赖**：整个方案只用到 `fetch`（Node 内置）与 `crypto`（Node 内置）。不引入任何 `.node` 模块、不引入构建期原生工具链。这一点是 Android 兼容的前提，见 [06](06-手机端兼容.md)。

## 7. 架构上的三个关键取舍

**取舍一：不做自有后端，代价是受 GitHub rate limit 约束。**
换来的是零运维、零成本、数据天然可被搜索引擎索引、作者收到的通知是 GitHub 原生通知。
缓解：分层 TTL 缓存 + 陈旧数据降级 + GraphQL 批量查询。

**取舍二：client UI 与独立页面 UI 是两套渲染路径，代价是视觉可能不一致。**
换来的是一条不依赖 client 注入的保底通路。
缓解：两者共用同一份数据契约与同一套 CSS 变量；先做独立页面（形态②），client 形态①后做。**先保底，再优化。**

**取舍三：先只接 2 个索引源，而不是全部 6 个。**
换来的是一致性与可控性。
理由：`dsh-find-plugins` 已经做过 7 源聚合，社区不需要重新证明这件事。索引源的多少不改变社区的价值主张。**优先补贴讨论层。**
