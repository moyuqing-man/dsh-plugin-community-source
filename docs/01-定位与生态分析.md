# 01 · 定位与生态分析

> 本文件回答三个问题：**为什么已经有市场了还要做社区？** **差异化在哪？** **我们明确不做什么？**

---

## 1. 结论先行

**市场已经过剩，社区还是空的。**

这不是主观判断，是一次跨 7 个源的实测结果：

| 源 | 条目数 |
|---|---|
| `dsh.so` | 10099 |
| `awesome-dsh-plugin` | 4579 |
| 岚叔目录 | 655 |
| `dsh-plugin-radar` | 301 |
| GitHub `dsh-plugin` topic | （全量索引） |
| npm registry 实时搜索 | （实时） |
| `dsh.works` registry | 抓取失败（CI 校验型） |
| **去重后候选池** | **约 13061 条** |

已有的市场项目（按 star 排序的代表）：

| 项目 | ★ | 定位 |
|---|---|---|
| `V1ki/dsh-plugin-subscriptions` | 448 | 订阅/更新追踪 |
| `awesome-dsh-plugin/dsh-find-plugin` | 183 | 发现与检索 |
| `bradeGithub/DSH-Plugins-Marketplace` | 175 | GitHub topic 全量索引，CI 每 2 小时刷新，带 `STANDARD.md` 识别层规范 |
| `Sanqi-normal/dsh-webui-market-plugin` | 104 | 目录（**审核 blocked / 风险 high**） |
| `Noob-stupid/dsh-plugin-hub` | 100 | Hub |

**它们全都在解决同一个问题：让用户找到插件。** 没有一个人在解决：**插件好不好用、坑在哪、作者还活着吗、这个需求有没有人一起做。**

## 2. 缺口到底在哪

把「使用一个第三方插件」的完整生命周期拆开：

| 阶段 | 谁在管 | 现状 |
|---|---|---|
| ① 发现 | 一堆市场 | ✅ 严重过剩 |
| ② 判断能不能用 | — | ❌ **缺口** |
| ③ 装上了但不会配 | README（如果有） | ❌ 缺口（README 质量参差） |
| ④ 用出 bug | GitHub Issues（如果作者开了） | ⚠️ 半缺口：分散在几千个仓库里，**没有任何聚合入口** |
| ⑤ 想评价/吐槽 | — | ❌ **缺口** |
| ⑥ 想要某个功能，不知道有没有人做 | — | ❌ **缺口** |
| ⑦ 自己想做插件，不知道从哪抄 | — | ⚠️ 缺沉淀（有一批人卡在「不知道插件怎么写」） |
| ⑧ 插件的更新/弃坑状态 | `dsh-plugin-subscriptions` | ✅ 部分解决 |

**②③⑤⑥⑦ 全是空的，而它们有一个共同特征：都需要「人」和「对话」，而不是「目录」。**

这就是社区的定位。

## 3. 社区是什么：一个「联合插件」

用户的原始构想非常准确：

> **社区本身也是一个「插件联合其他插件的联合插件」。**

这句话的工程含义是：**社区不建立自己的插件数据库。**

它做的是：

```
        ┌─────────────────────────────────────────────┐
        │  已有市场们（只读消费，不复制）              │
        │  dsh.so · awesome-dsh-plugin · radar ·       │
        │  DSH-Plugins-Marketplace · npm · GitHub      │
        └──────────────────┬──────────────────────────┘
                           │  读索引（不写回）
                           ▼
        ┌─────────────────────────────────────────────┐
        │  社区桥接层（本插件的 host 半边）            │
        │  · 把多源索引规范化为统一 PluginCard          │
        │  · 叠加 GitHub 维度：stars / issues / 更新   │
        │  · 叠加 Discussion 维度：帖子 / 评论 / 反应   │
        └──────────────────┬──────────────────────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        client slot    独立 HTTP     JSON API
        注入版 UI      页面版 UI      （原生客户端）
```

**「联合」的三层含义：**

1. **联合已有市场** —— 不重复收录，直接读它们的索引。哪个市场数据新就用哪个，互为备份。
2. **联合 GitHub** —— star / issue / discussion 全部桥接过来，不新建平行系统。
3. **联合插件作者与用户** —— 用同一个 GitHub 身份，让作者和用户在一个帖子里对话，而不是在 Issues 和 QQ 群之间来回跳。

## 4. 与前序项目的分工（重要：不是竞争）

| 已有项目 | 它做 | 社区做 | 关系 |
|---|---|---|---|
| 各市场 | 收录、检索、分类 | 不收录，只读它们的索引 | **消费方** |
| `dsh-plugin-subscriptions` | 订阅、更新提醒 | 展示「这个插件最近有人讨论」 | **互补** |
| GitHub Issues | bug 原始记录 | 聚合到插件详情页，并加上讨论上下文 | **桥接方** |
| GitHub Discussions | 帖子容器 | 提供 DSH 内的原生入口与体验 | **前端方** |
| 手机端 App | 连接、渲染 | 提供不依赖 client 注入的页面与 API | **被兼容方** |

**明确不做的四件事：**

1. ❌ **不做第二个插件目录。** 不维护自己的收录库，不写爬虫全集，不做审核规范（那已经有 `STANDARD.md` 了）。
2. ❌ **不做第二个注册系统。** 不存密码、不发验证邮件、不做找回流程。身份完全交给 GitHub。
3. ❌ **不做三个手机端 App。** 手机端已有成熟方案，我们改代码去适配它们，而不是再造一个。
4. ❌ **不做自有后端服务。** 没有服务器、没有数据库、没有域名。所有持久化落在 GitHub 上。

## 5. 差异化卖点（一句话版）

> **市场告诉你「有哪些插件」，社区告诉你「该不该用、怎么用、坑在哪、下一步会变成什么」。**

具体体现在五个功能：

| # | 功能 | 依托 | 为什么市场做不到 |
|---|---|---|---|
| 1 | **插件详情页带社区维度** | slot `plugins.detail.section` / `plugins.detail.badge` | 市场是目录页，没有「详情页挂讨论」的位置 |
| 2 | **一键把 issue 变成帖子** | GitHub Issues ↔ Discussions 互转 | 需要同时持有两边 API |
| 3 | **「我想要」需求板** | Discussions 的一个 category | 需求收集天然需要讨论，目录装不下 |
| 4 | **插件开发答疑** | Discussions 的一个 category | 沉淀「怎么写插件」，对应实测发现——大量人卡在这一步 |
| 5 | **登录即用，8 位码** | GitHub Device Flow | 市场大多只读，不需要身份；社区需要身份但必须极简 |

## 6. 用户原始设想的逐条落实

| 用户说过 | 落实情况 |
|---|---|
| 「有人做了市场，所以缺个社区」 | ✅ 实测验证：13061 条候选、8 个市场项目，确认市场过剩；社区缺口成立 |
| 「社区本身也是一个插件联合其他插件的联合插件」 | ✅ 落地为第 3 节的「不建库、只桥接」架构 |
| 「DSH 插件只做界面和链接层」 | ✅ host 半边 = API 桥接 + 缓存；client 半边 = 纯界面 |
| 「GitHub 本身已有 star 做评分」 | ✅ 不建评分系统，直接读 stars + discussion reactions |
| 「Issues 做 bug 汇报」 | ✅ 聚合到详情页，不另建工单 |
| 「简化 GitHub 注册流程」 | ✅ 升级为 Device Flow（[04](04-身份与登录.md)） |
| 「评论需要登录」 | ✅ 匿名可读、登录可写 |
| 「论坛载体选 GitHub Discussions」 | ✅ Categories → 板块映射 |
| 「手机软件 B 站已有，所以不用做手机端」 | ✅ 采纳，改为主动兼容 |
| 「要看它能不能兼容插件，不能就我们主动兼容」 | ✅ 三套方案的兼容矩阵见 [06](06-手机端兼容.md)；结论是**部分不能，且我们已有主动兼容方案** |

---

## 7. 定位的一句话总结

**社区 = 市场之上的信任层。**
它自己不是一个市场，而是一个**把若干市场、GitHub、插件作者和用户缝在一起**的联合体。它的存在价值不在于「多收录了多少插件」，而在于「让每一个已被发现的插件变得可判断、可讨论、可共建」。
