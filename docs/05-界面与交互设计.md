# 05 · 界面与交互设计

> 本文件回答：**社区长什么样？挂在哪些官方槽位上？关键流程怎么走？**
> 所有槽位名均来自 DSH 运行时 `client` 平台 Inspect Provider 的实时输出，可直接使用。

---

## 1. 信息架构

```
社区
├── 首页（发现）
│   ├── 最新帖子
│   ├── 热门讨论（按 upvote）
│   ├── 插件动态（有新版本 / 新讨论的插件）
│   └── 待解决问题（无回答的帖）
├── 板块（= GitHub Discussions Categories）
│   ├── 📢 公告
│   ├── 💬 综合讨论
│   ├── ❓ 使用求助          ← 有「答案」标记
│   ├── 🐛 问题反馈          ← 关联 Issues
│   ├── 💡 我想要（需求板）   ← GitHub Discussions Poll
│   ├── 🧩 插件开发          ← 沉淀「怎么写插件」
│   └── 🎨 作品展示
├── 插件（详情）
│   ├── 基本信息（名称 / 作者 / 版本 / 许可 / 仓库）
│   ├── 社区维度（stars / open issues / 最近提交 / 是否弃坑）
│   ├── ⭐ 社区讨论（关联帖子）
│   ├── 🐛 已知问题（聚合 Issues）
│   ├── 📖 使用心得（关联帖）
│   └── 安装入口
└── 我的
    ├── 我的帖子
    ├── 我参与的
    └── 登录 / 登出
```

**板块即 GitHub Discussions 的 Categories** —— 不在本地维护一份板块表。新增板块只需在 GitHub 上建一个 category，社区页自动出现。

## 2. 页面清单

| 页面 | 形态① 组件 | 形态② 路由 | 说明 |
|---|---|---|---|
| 社区首页 | `<CommunityHome>` | `/community` | 帖子流 + 筛选 |
| 帖子详情 | `<ThreadView>` | `/community/t?id=` | 正文 + 评论树 + 反应 |
| 发帖 | `<Composer>` | `/community/new?cat=` | 标题 / 正文 / 分类 / 关联插件 |
| 插件详情 | `<PluginCommunity>` | `/community/plugin?repo=` | 社区维度 + 讨论 + Issues |
| 插件列表 | `<PluginList>` | `/community/plugins` | 多源索引 + 社区热度排序 |
| 用户主页 | `<UserProfile>` | `/community/u?login=` | 该用户的帖子 |
| 登录面板 | `<DeviceFlowPanel>` | 浮层 | 8 位码 + 链接 + 二维码 |
| 设置 | `<CommunitySettings>` | `/community/settings` | client_id / owner / repo |

**形态①与形态②共用同一份数据契约**（`/api/v1/community/*`），区别只是渲染方式：
- 形态①：React 组件树，走 `ctx.slots` 注册，用 `--dsw-*` 主题变量。
- 形态②：host 侧拼 HTML 字符串 + 内联 CSS + 少量内联 JS。

> 实现顺序：**先做形态②**。它既是手机端的保底通路，也更简单（不需要构建工具链）。

## 3. 槽位挂载方案

### 3.1 P0：三个必做槽位

#### ① `sidebar.panellist`（list）—— 侧栏社区入口

```js
ctx.slots.inject('sidebar.panellist', () =>
  ctx.slots.register({ name: 'sidebar.panellist', id: 'dsh-community-nav', order: 50 }, CommunityNavIcon));
```

**为什么挂这里**：这是全局面板图标区，是用户进入任何「一级页面」的标准入口。

#### ② `main`（keyed，key = 侧栏派发的入口 id）—— 社区全屏主页

```js
ctx.slots.inject('main', () =>
  ctx.slots.register({ key: 'community' }, CommunityApp));
```

**关键**：`main` 是 **keyed** 槽位，key 由侧栏派发的入口 id 决定。上面 `sidebar.panellist` 注册的入口派发的 id **必须与这里一致**（都用 `community`），点击才会切到社区页。

> 实测说明：`main` 的 `keyDomain` 是 open any string，目前只占用了 `conversation`。社区用 `community` 不会冲突。

#### ③ `plugins.detail.section`（list）—— 插件详情页里的社区区块

```js
ctx.slots.inject('plugins.detail.section', () =>
  ctx.slots.register({ name: 'plugins.detail.section', id: 'dsh-community-plugin-section', order: 20, label: '社区讨论' }, PluginCommunitySection));
```

**为什么这是杀手锏**：DSH 官方专门为「扩展现有插件页」留了这组座位——用户在看插件详情时，**同一屏内**就能看到社区讨论和已知问题，不需要跳出去。这是任何独立市场都做不到的位置优势。

### 3.2 P1：增强槽位

| 槽位 | 注册内容 | 效果 |
|---|---|---|
| `plugins.detail.badge` | 「🔥 讨论活跃」/「⚠️ 有已知坑」标签 | 在插件标题旁，排在版本/beta/问题标签之后 |
| `plugins.detail.actions` | 「去提问」按钮 | 详情页头部，在自带 switch/uninstall **之前** |
| `settings.section` | 社区设置页 | client_id / owner / repo / 缓存 / 登出 |
| `shell.overlay` | Device Flow 浮层 | 全局可用，任意页面点登录都能弹出 |
| `conversation.input.left` | 「引用社区帖」按钮 | 把社区帖子带进对话上下文 |

### 3.3 P2：深度整合

| 槽位 | 注册内容 | 效果 |
|---|---|---|
| `tool.call.toolview`（keyed，按 wire tool name） | `community_search` / `community_post` 的自定义卡片 | Agent 调用社区工具时显示漂亮的讨论卡片而不是纯文本 |
| `conversation.chat.turnTail` | 「这个问题社区有人问过」提示 | Agent 答完后主动提示社区里有相关讨论 |
| `sidebar.footer.action` | 「我的帖子 / 待回复」 | 侧栏底部计数 |

### 3.4 槽位挂载总览图


## 4. 关键交互流程

### 4.1 首次使用（冷启动）

```
用户点侧栏「社区」
    │
    ▼
社区首页（匿名可读）
    │
    ├─ 若 Config 里没配 client_id / owner / repo
    │     └─► 显示「一键接入」引导页
    │           1. 说明这是社区插件，数据来自 GitHub
    │           2. 给出「创建 OAuth App」的分步图示（含 Enable Device Flow 那一步）
    │           3. 填 client_id → 保存
    │           4. 填社区仓库 owner/repo（或用默认的官方社区仓库）
    │
    └─ 配置就绪 → 正常显示帖子流
```

**设计要点**：冷启动引导必须**内联在页面里**，不能只写在 README。实测经验是——绝大多数人卡在「读完 README 也不知道下一步点哪」。

### 4.2 登录（Device Flow）

```
点「用 GitHub 登录」
    │
    ▼
shell.overlay 弹出 DeviceFlowPanel
    ┌──────────────────────────────────────┐
    │   用 GitHub 登录                       │
    │                                       │
    │       ┌───────────────┐               │
    │       │  WDJB-MJHT    │  [复制]        │
    │       └───────────────┘               │
    │        [ 二维码 ]                      │
    │                                       │
    │   [ 打开 github.com/login/device ]     │
    │                                       │
    │   ⏳ 等待授权…（剩余 14:32）           │
    └──────────────────────────────────────┘
    │
    ▼  前端每 interval 秒调 /api/v1/community/auth/poll
    │
    ├─ pending  → 继续转圈
    ├─ slow_down→ 前端把间隔 +5s
    ├─ ok       → 关闭浮层，右上角出现头像
    ├─ expired  → 显示「已过期，重新获取」
    └─ denied   → 显示「已取消」
```

**移动端优化**：二维码 + 复制按钮同时给。手机用户直接长按复制，电脑用户扫码用手机授权。

### 4.3 「这个插件能不能用」——核心场景

这是社区相对市场的**唯一不可替代场景**，必须做顺：

```
用户在某处看到一个插件名（比如从市场、从别人推荐）
    │
    ▼
在社区搜索框输入插件名
    │
    ▼
插件列表（多源索引 + 社区热度）
    │  每张卡显示：
    │    · 名称 / 一句话描述 / 作者
    │    · ⭐ stars  ·  🐛 3 个未解决  ·  🕐 2 个月前更新  ·  ⚠️ 未归档
    │    · 💬 8 个讨论  ·  🔥 本周活跃
    ▼
点进插件详情
    │
    ├─ 顶部：能不能用的最终判断
    │    ⭐ 175   🐛 3 open   🕐 2 月前更新   ✅ 活跃维护
    │
    ├─ 🐛 已知问题（聚合 Issues，标题 + 状态 + 更新时间）
    │      点任意一条 → 展开正文（不跳转 GitHub）
    │
    ├─ 💬 社区讨论（关联帖子）
    │      已解决的排前面，带 ✅ 答案标记
    │
    └─ 📖 使用心得
    │
    ▼
用户做出判断 —— 装 / 不装 / 换一个
```

**对比市场**：市场到「描述 + stars」就结束了。社区把「未解决问题数、最近更新、是否归档、有没有人讨论、坑在哪」全部摊在同一屏上。

### 4.4 一键把 Issue 变成帖子

```
插件详情页 · 已知问题列表
    每条 Issue 右侧有  [ 💬 在社区讨论 ]  按钮
        │
        ▼
    打开发帖编辑器，预填：
        标题 = Issue 标题
        正文 = Issue 正文摘要 + 原链接
        分类 = 🐛 问题反馈
        关联 = 该插件
```

**为什么这个功能重要**：Issue 是「我和作者」的一对一，Discussion 是「我和所有遇到这个问题的人」。把 Issue 提升为 Discussion 是社区最直接的增值动作。

### 4.5 Agent 参与（形态④的自然延伸）

```
用户在对话里说：「我想找个能做 X 的插件」
    │
    ▼
Agent 调 community_search { query: "X" }
    │
    ▼
返回：
   · 匹配的插件卡片（含 stars / issues / 活跃度）
   · 相关讨论摘要（「有人问过类似问题，答案是…」）
    │
    ▼
Agent 给出带社区依据的推荐，而不是只列名字
```

**这是社区与 DSH 结合得最紧的地方**：Agent 不只能搜「有哪些插件」，还能搜「别人用这些插件踩过什么坑」。

## 5. 视觉设计原则

| 原则 | 做法 |
|---|---|
| **跟随主题** | 只用 DSH 的 `--dsw-*` CSS 变量（实测 `dsh-workspace` 用的就是 `var(--dsw-alias-label-primary, #172033)` 这种带 fallback 的写法） |
| **不引入 UI 框架** | 不引 Tailwind / MUI / Antd。内联样式 + 少量 CSS 变量，保持零构建依赖 |
| **内容优先** | 社区页大量是文本内容，排版以可读性为先（行宽、行高、代码块样式） |
| **两种形态同一套 CSS 变量** | 形态②的内联 `<style>` 里同样写 `var(--dsw-*)`，在 DSH 里自动跟随主题；在裸浏览器里有 fallback 色值 |
| **移动优先的容器** | 社区页在窄屏下必须单列可用（形态②会直接在手机 WebView 里打开） |

**样式注入方式**（实测自 `dsh-workspace`）：

```js
ctx.effect(() => {
    if (document.getElementById(STYLE_ID)) return;
    const style = document.createElement('style');
    style.id = STYLE_ID;
    style.textContent = STYLES;
    document.head.append(style);
    return () => style.remove();
}, 'dsh-community: styles');
```

## 6. 与「插件详情页」共存的注意事项

`plugins.detail.section` 是 list 槽位，页面上可能同时有 DSH 自带的区块和别的插件注入的区块。所以：

- **高度要自适应**，不要写死 `100vh`。
- **不要抢占焦点**，不要自动展开、不要自动播放。
- 默认显示**摘要**（「社区讨论 · 3 个帖子」），点开才加载详情——避免拖慢插件详情页首屏。
- 用 `order` 把自己排在其他区块之后（`order: 20` 起步），不要插到自带内容前面。

## 7. 无障碍与国际化

| 项 | 做法 |
|---|---|
| 键盘可达 | 所有按钮/链接可 Tab 到；浮层 Esc 关闭 |
| 语义标签 | 帖子列表用 `<article>`，评论树用嵌套 `<ol>` |
| 对比度 | 只用主题变量 + 保证 fallback 色值对比度 ≥ 4.5:1 |
| 语言 | 中文优先，同时输出 `en`；文案全部走词条表，不硬编码在组件里 |
| 时间 | 用相对时间（「2 个月前」）+ `title` 属性放绝对时间 |

## 8. 界面层不做什么

1. ❌ **不做富文本编辑器。** Markdown 纯文本域 + 预览切换即可（GitHub 本身就是 Markdown）。
2. ❌ **不做图片上传。** GitHub 的 Markdown 支持拖拽上传，但需要图床。P0 只支持粘贴图片 URL。
3. ❌ **不做实时推送。** 不做 WebSocket。刷新即更新，避免长连接在手机弱网下变成负担。
4. ❌ **不做私信。** 私信不是社区，是 IM。DSH 本身有 IM 能力，不要把两件事混在一起。
5. ❌ **不做自己的通知系统。** 通知用 GitHub 原生的——你在社区发的帖有人回复，GitHub 会给你发邮件/通知。
