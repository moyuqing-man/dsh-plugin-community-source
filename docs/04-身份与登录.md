# 04 · 身份与登录

> 用户的核心诉求：**「简化 GitHub 注册流程」**。
> 本文件给出的答案是 **GitHub Device Flow**——一个 8 位验证码，没有回调域名、没有 client secret、没有注册表单，而且在手机上比在电脑上还顺手。

---

## 1. 为什么是 Device Flow

把三种可选方案摆在一起：

| 方案 | 用户操作 | 工程成本 | 手机端体验 |
|---|---|---|---|
| **自建注册** | 填邮箱 → 收验证码 → 设密码 → 验证 → 找回流程 | 后端 + 数据库 + 邮件服务 + 反滥用 | 一般 |
| **OAuth 网页回调** | 点登录 → 跳转 GitHub → 授权 → 跳回来 | 需要**回调域名 + HTTPS + client secret** | ❌ 本地服务做回调很别扭 |
| **Device Flow** ✅ | 点登录 → 看到 8 位码 → 点链接 → 输码 → 授权 | **只要一个 client_id** | ✅ 最好（手机输码比在电脑上跳转更顺） |

**决定性理由**：DSH 是一个**本地运行**的 harness。它的 Web 服务跑在 `127.0.0.1:19387` 之类的回环地址上，用户也可能通过中继域名访问（`dsh-phone-pair` 就是 `https://<id>.dsh-market.com`）。

要求「回调到 `http://127.0.0.1:xxxx/callback`」在桌面还勉强可行，一旦手机通过中继访问就会彻底失效——回调地址是电脑的，手机上的浏览器跳过去会打到别的地方。

**Device Flow 没有回调。** 它只需要*出站* HTTP 请求，从任何网络位置都能工作。

## 2. Device Flow 完整流程

### 2.1 时序图

```
       用户              DSH 社区插件 (host)          GitHub
        │                     │                        │
        │  点「用 GitHub 登录」 │                        │
        ├────────────────────►│                        │
        │                     │ POST /login/device/code │
        │                     ├───────────────────────►│
        │                     │◄───────────────────────┤
        │                     │ device_code (保密)      │
        │                     │ user_code = "WDJB-MJHT" │
        │                     │ verification_uri        │
        │                     │ expires_in=900, interval=5
        │                     │                        │
        │  ┌──────────────────┴────────────────────┐   │
        │  │  显示大号 8 位码 + 一个按钮/二维码       │   │
        │  │  「复制验证码」 「打开 github.com/login/device」
        │  └──────────────────┬────────────────────┘   │
        │                     │                        │
        │  用户在浏览器输入码并授权（手机/电脑均可）      │
        ├─────────────────────────────────────────────►│
        │                     │                        │
        │                     │ 每 interval 秒轮询一次  │
        │                     │ POST /login/oauth/access_token
        │                     ├───────────────────────►│
        │                     │◄─ error: authorization_pending （继续等）
        │                     │◄─ error: slow_down （间隔 +5s）
        │                     │◄─ access_token 🎉       │
        │                     │                        │
        │                     │ 存 ctx.credentials      │
        │◄────────────────────┤ 前端只收到 {login, avatar}│
        │  「已登录为 @xxx」    │                        │
```

### 2.2 第 1 步：申请设备码

```
POST https://github.com/login/device/code
Accept: application/json
Content-Type: application/json

{ "client_id": "<公开的 client_id>", "scope": "read:user public_repo" }
```

响应：

```json
{
  "device_code": "3584d83530557fdd1f46af8289938c8ef79f9dc5",
  "user_code": "WDJB-MJHT",
  "verification_uri": "https://github.com/login/device",
  "expires_in": 900,
  "interval": 5
}
```

> **`device_code` 绝不能给前端。** 前端只需要 `user_code`、`verification_uri`、`expires_in`、`interval`。
> 若响应里带 `verification_uri_complete`（把码预先填进 URL 的形式），优先给用户这个链接，可以少一步输入。

### 2.3 第 2 步：用户授权

用户打开 `https://github.com/login/device`，输入 `WDJB-MJHT`，点授权。

**这一步是 GitHub 的页面，不是我们的。** 不需要我们做任何 UI，不需要处理密码、2FA、SSO——全部由 GitHub 负责。

### 2.4 第 3 步：轮询取 token

```
POST https://github.com/login/oauth/access_token
Accept: application/json
Content-Type: application/json

{
  "client_id": "<公开的 client_id>",
  "device_code": "<第 1 步的 device_code>",
  "grant_type": "urn:ietf:params:oauth:grant-type:device_code"
}
```

按 `interval` 秒轮询。可能的响应：

| `error` | 含义 | 处理 |
|---|---|---|
| `authorization_pending` | 用户还没授权 | 继续等，不报错 |
| `slow_down` | 轮太快 | **间隔 +5 秒**，继续等 |
| `expired_token` | 900 秒过期 | 停止，重新发起流程 |
| `access_denied` | 用户拒绝 | 停止，提示「已取消」 |
| `incorrect_client_credentials` | client_id 错 | 配置错误，记日志 |
| `device_flow_disabled` | App 未开启 Device Flow | **配置错误**，见第 5 节 |

成功：

```json
{ "access_token": "gho_xxxxxxxx", "token_type": "bearer", "scope": "read:user,public_repo" }
```

### 2.5 第 4 步：落库

```js
// host 侧，token 只在这一层出现
ctx.credentials.set(COMMUNITY_GITHUB_REF, access_token)
```

然后 `GET https://api.github.com/user` 拿 `login` / `avatar_url`，返回给前端：

```json
{ "status": "ok", "login": "someuser", "avatarUrl": "https://..." }
```

**前端从始至终看不到 token。**

## 3. 权限范围（Scopes）

> ⚠️ **本节经过实测修正。** 早期草稿写的 `read:discussion` / `write:discussion` **不是 OAuth scope**（它们是 GitHub App 的 permission 名，两套体系）。写进 `scope` 参数不会生效。详见 [08](08-GitHub-API-契约.md) 第 4 节。

| Scope | 用途 | 是否必须 |
|---|---|---|
| **`read:user`** | 读自己的 `login` / `avatar_url` | ✅ |
| **`public_repo`** | **在公开仓库建讨论 / 发评论 / 加 reaction** | ✅ **写路径必须** |
| `offline_access` | 拿 refresh token（access 8h / refresh 6 个月） | 可选 |
| `repo` | ❌ **不要**。私有仓库才需要，会吓退用户 |
| ~~`read:discussion`~~ | ❌ **不存在** | — |
| ~~`write:discussion`~~ | ❌ **不存在** | — |

📄 官方原文（Discussions GraphQL 指南）：
> *Access tokens require the `repo` scope for private repositories and the **`public_repo` scope for public repositories**.*

**所以社区请求的 scope 是 `read:user public_repo`。**

**为什么 `public_repo` 是必要的而不是过度的**：它只覆盖**公开**仓库的读写。社区讨论本来就发生在公开仓库里，且这是 GitHub 官方指定的写入 scope。相比之下 `repo` 会连**私有仓库**一起授权——那才是应该拒绝的。

> **读路径不需要任何 scope。** 公开仓库的 Discussions 有 REST 读接口且**完全免登录**（✅ 实测，见 [08](08-GitHub-API-契约.md) 第 1 节）。
> 这一点很关键：**匿名用户不登录也能看论坛**，登录只在要写字的时候才发生。

**「最小权限」的真正含义**：不是「scope 越少越好」，而是**在恰好够用的前提下不碰私有数据**。`read:user public_repo` 就是这个平衡点。

## 3.5 写操作的次级限流（必须给发帖按钮做节流）

📄 官方对**内容创建**的独立限制：**≤ 80 次/分钟 且 ≤ 500 次/小时**，且「**网页界面操作 + REST + GraphQL 全部计入**」。

这意味着**社区刷得太勤会拖累用户在 GitHub 网页上的正常使用**。必做：

| 项 | 做法 |
|---|---|
| 前端节流 | 发帖/评论按钮提交后立即置灰，直到响应返回 |
| 请求间隔 | mutative 请求之间**至少 1 秒**（官方 best practice） |
| 幂等 | 同一内容短时间内重复提交直接拒绝，**不转发给 GitHub** |
| 退避 | 收到 403/429：有 `retry-after` 按其等待；`x-ratelimit-remaining: 0` 则等到 `x-ratelimit-reset`；否则至少等 1 分钟再指数退避 |
| **绝不硬重试** | 📄 持续重试**可能导致 integration 被封禁** |

> 反垃圾的第一道防线是 GitHub 的 abuse detection，但 📄 **审核责任仍在仓库维护者**（giscus README：「You can moderate the comments on GitHub」）。**托管到 GitHub ≠ 有人替你审贴。**

## 4. 登录态在 UI 上的三种状态

| 状态 | 判定 | 界面表现 |
|---|---|---|
| **匿名** | `/api/v1/community/me` → `{authenticated:false}` | 全部内容可读；发帖/评论/投票按钮变为「登录后参与」，点击弹 Device Flow 面板 |
| **已登录** | `{authenticated:true, login, avatarUrl}` | 右上角显示头像 + 用户名；写操作直接可用 |
| **已登录但 token 失效** | GitHub 返回 401 | 静默清除凭据，回落到匿名态，**不弹错误**，只在写操作时提示重新登录 |

**核心原则：读永远不需要登录。** 这是社区能被搜索引擎索引、能被匿名用户直接打开的前提。

## 5. 一次性配置（作者侧，不是用户侧）

使用者需要做一次配置（写进插件 Config 或首次引导）：

1. 打开 https://github.com/settings/developers → **New OAuth App**
2. 任意填 Application name 与 Homepage URL（Device Flow 不看这两个值）
3. **Authorization callback URL 随便填一个合法 URL**（Device Flow 不使用它，但表单必填）
4. 创建后拿到 **Client ID**（公开值）
5. 在该 OAuth App 设置页把 **Enable Device Flow** 勾上 ← **这一步漏了会得到 `device_flow_disabled`**
6. 把 Client ID 填进社区插件配置

> **OAuth App 不需要 Client Secret。** Device Flow 的设计前提就是「公开客户端」。
> 这也意味着社区插件**不需要任何服务端秘密**，可以直接开源、可以被任何人自建实例。

### 5.1 选 OAuth App，不选 GitHub App（实测结论）

两者的 `scope` 语义**完全不同**：

| | OAuth App ✅ 选它 | GitHub App |
|---|---|---|
| 权限由什么决定 | `scope` 参数（`public_repo` 等） | App 上配置的 permissions |
| device flow 里传 `scope` | ✅ 有效 | ⚠️ **只接受 `offline_access`** |
| 配置复杂度 | 只要一个 client_id | 要私钥、要安装到仓库、权限面更宽 |

📄 官方原文（GitHub App device flow）：*This parameter does not control permissions for the user access token.*

→ 本方案用 **OAuth App**。另外注意：**`client_secret` 在整个流程里都不需要**，所以插件包里不能也不需要出现任何秘密。

### 5.2 两个兜底登录方式（可选，P2）

| 方式 | 优点 | 代价 |
|---|---|---|
| **复用 `gh` CLI**：`gh auth token` | 已装 gh 的用户**零配置**直接登录 | ⚠️ 该命令**直接输出 token 明文**，是「读取显示」不是安全代理；仅在用户明确选择时使用 |
| **手动粘贴 PAT** | 零基础设施，任何环境可用 | 用户要自己去建 token 并选 scope，体验最差 |

**建议**：Device Flow 为默认，PAT 为兜底，`gh` 为「检测到 gh 已登录」时的加速选项。三者都接到同一个 `ctx.credentials` 存取层，上层无感知。

## 6. 登录流程的「简化」体现在哪

对照用户原始诉求「简化 GitHub 注册流程」，本方案把操作压到极限：

| 步骤 | 用户要做的事 |
|---|---|
| 1 | 点「用 GitHub 登录」 |
| 2 | 看见 `WDJB-MJHT`，点「复制」 |
| 3 | 点「打开 GitHub」（新标签页） |
| 4 | 粘贴码，点 Continue |
| 5 | 点 Authorize |

**5 步，无表单、无邮箱、无密码、无验证邮件、无找回流程。**
对比自建账号系统动辄 6–8 步且需要信任一个陌生服务，这里用户授权的是一个**他本来就信任的账号**。

**进一步简化的可选项（P2）**：
- 若 GitHub 返回 `verification_uri_complete`，第 2 步可以直接省成「点这个链接」。
- 生成二维码（`qrcode-generator` 这类**纯 JS** 库，零原生依赖），手机扫码直接到授权页。
  > ⚠️ 注意 `dsh-mobile-bridge` 用了 `qrcode-generator@1.4.4`——它是纯 JS 的，符合零原生依赖红线。

## 7. 安全清单

| 项 | 做法 |
|---|---|
| token 存储 | `ctx.credentials`（DSH 自带），**插件自己不落盘** |
| token 暴露面 | 只在 host 侧的 GitHub 调用中出现；**永不返回前端、永不写日志** |
| 独立页面 / JSON API 访问面 | 默认 `isLoopback(req)` 仅本机；远程需显式开 `allowRemote` |
| 写操作校验 | host 侧二次校验登录态，不信任前端传来的任何身份信息 |
| CSRF | 写接口要求 `Content-Type: application/json` + 自定义头；独立页面场景下校验 `Origin` |
| 错误信息 | 不出现 token、不出现绝对路径；统一信封 `{status, reason, message, fields, requestId}` |
| 登出 | `ctx.credentials.unset(ref)`，清缓存 |

## 8. 需要验证的一个关键假设（M0 必做）

**假设**：任何 GitHub 用户（只要有 public repo 的读权限）都能在社区自己的 Discussions 仓库里**新建 Discussion**。

**依据**：GitHub 官方文档在「参与讨论」页的权限框明确写着：

> *People with read access to a repository can participate in discussions and polls in the repository.*
> —— [GitHub Docs · 参与讨论](https://docs.github.com/zh/discussions/collaborating-with-your-community-using-discussions/participating-in-a-discussion)

**风险**：该表述的「participate」是否无歧义地涵盖「新建 Discussion」，需要实测确认。如果不能，会直接影响「论坛」这一载体。

**备选方案（已准备好，不需要重新设计）：**

| 备选 | 做法 | 代价 |
|---|---|---|
| B1 | 写路径改为 **Issues**（公开仓库任何用户都能开 Issue），再自动同步为 Discussion | 需要一个同步动作；Issue 界面没有 upvote |
| B2 | 社区自建一个 GitHub Organization，Discussions 开在 org 级 | org 配置更复杂 |
| B3 | 接受「帖子只能由维护者代发」，用户走 Issue 提交、维护者转帖 | 交互变重，不推荐 |

**M0 的验收动作**：用一个**非协作者的普通 GitHub 账号**，对社区仓库尝试创建 Discussion，记录结果。三小时内可完成。

## 9. 与 DSH 授权体系的整合（可选）

DSH 提供 `ctx.authorization.registerFlow` / `begin`，可以让插件接入 harness 自己的授权 UI，而不是自己画面板。

**建议**：
- **P0 阶段不用它**，自己画 Device Flow 面板（因为要在独立页面形态②里也能用，那里没有 harness UI）。
- **P1 阶段**在 client 形态①里接 `authorization`，让桌面端体验更原生。
- 无论用哪种，**token 的存取一律走 `ctx.credentials`**。
