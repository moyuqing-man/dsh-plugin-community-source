# 06 · 手机端兼容

> 用户的表态：**「手机软件在 B 站已经有了，所以不用做手机端；但要看它能不能兼容插件，不能就我们主动兼容。」**
>
> 本文件给出调研结论：**三套手机方案里，一套天然兼容，两套不能——而这两套都不需要它们改，我们改自己就行。**

---

## 1. 结论速览

| 手机方案 | 形态 | 能渲染 client 插件吗 | 社区能否工作 | 我们要做的事 |
|---|---|---|---|---|
| **`yhm080315-sudo/dsh-android`** | 完整 DSH 打包成 APK（同源真 DSH） | ✅ **能** | ✅ 形态①②③④全部可用 | 只需守住「零原生依赖」红线 |
| **`Zoragyx/dsh-phone-pair`** | WebView 外壳 + 构建时前端快照 | ❌ **大概率不能** | ⚠️ 形态①不行，**形态②可用** | 提供独立页面 + 首次访问引导 |
| **`Hakunm/dsh-android-app`** | 原生 Jetpack Compose 客户端 | ❌ 不渲染 Web | ⚠️ 形态①不行，**形态③可用** | 提供稳定 JSON API |

**一句话**：**不做手机端，但让社区在三种手机端上都有可用形态。**

## 2. 方案一：`dsh-android` —— 天然兼容 ✅

### 2.1 它是什么

把**完整的 DSH** 打包成一个独立 APK：自带 Node 运行时 + Termux bionic 二进制，**不需要 Termux、不需要 proot、不需要 root、不需要电脑**。

README 原文（决定性证据）：

> **「WebView 里是真正的 DSH Web 界面——不是重写的，是同源代码」**
> 「主界面、插件、皮肤、agent 全部跟桌面端一致」

对比表中：**第三方插件 ✅**。

### 2.2 为什么它兼容

因为它的 WebView 里跑的就是**同一个 `dsh web` 进程**——同样的 `clientModules` 服务、同样的 `__DSH_BOOT__` 注入、同样的 client 插件图。插件的 client 半边能正常加载。

**它就是一个 Android 上的 DSH host。** 对社区插件来说，它和桌面端没有区别。

### 2.3 但它是**最严苛**的运行环境

正因为它是「真 DSH」，社区插件要想在上面跑，必须满足它的约束。实测的限制：

| 约束 | 说明 |
|---|---|
| **任何依赖预编译 `.node` 的 npm 包都没有 Android 版本** | 原生模块是死路。`node-pty`、`better-sqlite3`、`sharp` 之类全部不可用 |
| `@vscode/ripgrep-android-arm64` npm 不发布 | 导致 `grep`/`glob` **100% 不可用**，需特殊修法 |
| 解包后约 600 MB，APK 约 130–180 MB | 体积约束 |
| `targetSdk` 必须是 28 | Android 10+ 的 W^X 禁止执行写出来的文件，故无法上架 Google Play |
| 无 iOS | iOS 不允许 fork/exec |
| 首次启动解包约 6 秒 | 冷启动体验 |

### 2.4 它的踩坑文档里与社区相关的关键条目

来源：该项目的 `docs/PITFALLS.md`。

| # | 现象 | 根因 | 正解 |
|---|---|---|---|
| 1 | glibc/musl 二进制被 seccomp 杀（`exit=159` = 128+SIGSYS） | 判据是**是否注册 `rseq`**，不是 libc 品牌 | 只有 bionic 能跑 |
| 2 | `flock is not supported on android-arm64` | Android 不实现 flock | 换锁策略 |
| 3 | `EACCES ... permission denied, link` | `link(2)` 被拒 | **不能退化成 `copyFile`**（破坏原子性 → `corrupt session log: invalid committed event at line 991: released v2 row 990 has seq gap`，整会话报废）；正解是「锁文件(O_EXCL) + rename」 |
| 4 | **客户端插件图为空 → 页面只有 3709 字节** | client 插件扫描在 **profile 目录**下解析 `node_modules`；profile 里没有 `node_modules` 则 `__DSH_BOOT__` entries 为 `[]` | 保证 profile 下有可达的 `node_modules` |
| 5 | 裸包名按 loader 自身位置解析 | Android 无 Node 内部加载器时 `else return await import(name)` 会从运行时安装目录找 | `pathToFileURL(createRequire(baseUrl).resolve(name)).href` |
| 6 | `grep`/`glob` 完全不可用 | `@vscode/ripgrep-android-arm64` 未发布 | 复制 bionic `rg` 到该平台包目录 |

**第 4 条对社区插件特别重要**，因为它给出了**唯一可靠的兼容性判据**：

> **页面 HTML `34846` 字节 = 插件图正常；`3709` 字节 = 插件图为空。**

这个判据在验收时可以直接用（见 [07](07-路线图与验收.md)）。

### 2.5 它对社区插件的硬性要求

```
🔴 红线一：纯 JS，零原生依赖
   ✗ node-pty  ✗ better-sqlite3  ✗ sharp  ✗ canvas  ✗ 任何 .node
   ✓ fetch（Node 内置）  ✓ crypto（Node 内置）  ✓ 纯 JS 库

🔴 红线二：不写构建期原生工具链
   ✗ 需要编译才能安装的依赖
   ✓ 纯 ESM 源码直接发布

🔴 红线三：不用 flock / 不用 link(2) 做原子写
   ✓ 锁文件（O_EXCL）+ rename
```

**本方案自身完全满足这三条**——它只用 `fetch` 和 `crypto`，缓存走 DSH 的 `ctx.storage`，不做文件原子写。见 [02](02-总体架构.md) 第 6 节的工程量表。

## 3. 方案二：`dsh-phone-pair` —— 不能，我们主动兼容 ⚠️

### 3.1 它是什么

**B 站视频 BV1RCpE6NEwu** 介绍的那套。安卓 WebView 外壳 App（`com.dsh.phone.pair`，minSdk 26 / targetSdk 34，只有 `INTERNET` + `ACCESS_NETWORK_STATE` 权限）。

包内嵌 **约 28 MB / 85 个内容哈希的前端资源**——这些资源是从**使用者自己电脑的 DSH Web GUI 构建时抓取的静态文件**，通过 `AssetIndex` + 同源闸门 + `/pair-app.sw.js` service worker 接管。

**它本身不是 DSH host，只是界面。** 真 DSH 与 Agent 都跑在电脑上，**电脑关机就完全不可用**（README 明确：「前端内置」不等于「离线可用」）。

连接链路：

```
手机 App ──► https://<16位>.dsh-market.com （固定中继域名）
                      │
                      ▼
             电脑侧插件 @linxin666/dsh-remote-web-ui
             （自带 cloudflared，autoTunnel:true + relay:true）
                      │
                      ▼
             电脑上的 DSH web 服务
```

配对：电脑生成配对链接 `https://<id>.dsh-market.com/pair-accept?pair=<32位配对码>`（**10 分钟过期**）→ 手机拿到**一年有效**的 HttpOnly 设备凭据（`dsh_pair` Cookie），最多 4 台设备（`maxDevices`）。

### 3.2 为什么它**不能**渲染 client 插件

这是本方案里最重要的一条技术判断：

| 事实 | 含义 |
|---|---|
| 手机端前端是**构建时快照**（85 个内容哈希静态资源，打包进 APK） | 快照生成的那一刻，**还不知道用户会装哪些插件** |
| DSH 的 client 插件是**运行时注入**（`clientModules` 动态 `fetchBundle`，写入 `__DSH_BOOT__` entries） | 插件 bundle 不在快照里 |
| 快照带**同源闸门**（AssetIndex 校验 85 个资源，`hits: 85 / misses: 0`） | 未在索引里的资源请求会被拦截 |
| 验证脚本显示 `bridge.js` **按设计不内置** | 说明作者已经意识到「有些东西不能快照」 |

**推论**：该内置前端很可能拿不到、也不会加载插件的 client bundle。**结果是「插件 UI 不显示」——而且是静默的**，页面上什么都没有，用户会以为插件没装。

**这与 `dsh-android` 的坑 #4 是同一类故障**（插件图为空），但根因不同：
- `dsh-android`：profile 下没有 `node_modules` → 可以修（服务端问题）
- `dsh-phone-pair`：前端是预打包快照 → **修不了**（客户端问题）

### 3.3 我们的主动兼容：形态②（独立 HTTP 页面）

**核心思路**：既然它的前端快照装不下我们的 client 插件，那就**让社区页不需要 client 插件**。

社区插件在 host 侧注册一条**独立路由**（见 [03](03-插件实现规格.md) 4.1）：

```js
ctx.effect(() => webServer.register({
    kind: 'exact', path: '/community',
    async handler(req, res) {
        res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8', 'Cache-Control': 'no-store' });
        res.end(renderCommunityHomeHtml());   // 完整 HTML 字符串
    },
}));
```

**这样：**

```
手机 dsh-phone-pair 的 WebView 访问
    https://<id>.dsh-market.com/community
        │
        ▼
    电脑上的 DSH web 服务
        │
        ▼
    社区的 host 半边直接返回整页 HTML
        │  不经过 __DSH_BOOT__，不依赖 client 插件图
        ▼
    ✅ 手机上看得到完整社区
```

**为什么这条路一定成立**：`webServer.register` 的 `handler` 拿的是**原生 Node 的 `req`/`res`**（实测自 `dsh-workspace`），可以 `res.end()` 任意内容。而 `/community` 这个 URL 会经由中继域名原样转发到电脑的 DSH web 服务——**中继转发的是 HTTP 请求，不是资源文件**，所以不受 AssetIndex 同源闸门约束。

> ⚠️ **需要实测确认**：中继是否只放行产品自带路径、是否会把未知路径也转发。这是 M1 的一个验证项。
> 若中继做了路径白名单，退路是让用户**用手机浏览器直接打开** `https://<id>.dsh-market.com/community`（浏览器没有同源闸门）——这依然成立，只是少了 App 内的集成感。

### 3.4 具体的兼容动作清单

| # | 动作 | 说明 |
|---|---|---|
| 1 | host 侧实现 `/community` 系列独立页面 | 保底通路，P0 |
| 2 | 首页顶部加一条**环境提示条** | 检测「client 插件图未加载」时显示：「你的手机客户端无法显示插件界面，点这里在浏览器中打开社区 →」 |
| 3 | 提供**短链/二维码** | 在桌面端的社区设置页生成 `https://<id>.dsh-market.com/community` 的二维码，手机扫码直达 |
| 4 | 页面**移动优先** | 独立页面的 CSS 必须窄屏单列可用（因为这是它唯一的手机端形态） |
| 5 | 不做 App 内嵌假设 | 所有功能都假设「可能没有 shell、可能没有 client runtime」 |

### 3.5 检测「client 插件图是否为空」

用 `dsh-android` 项目给出的同一个判据：

```js
// 桌面端 / 任意 DSH 的 host 侧
const html = await (await fetch('http://127.0.0.1:<port>/')).text();
const pluginGraphOk = html.length > 10000;   // 34846 ≈ 正常，3709 ≈ 插件图为空
```

社区页面在检测到 `pluginGraphOk === false` 时，主动引导用户去独立页面。

## 4. 方案三：`dsh-android-app` —— 不能，但提供 JSON API ⚠️

### 4.1 它是什么

**`Hakunm/dsh-android-app`** —— 原生 **Jetpack Compose + Material 3** Android UI，AGPL-3.0。**它根本不渲染 Web**，所以 client 插件和它没有任何关系。

它通过服务端插件 `dsh-workspace`（v1.0.0）连接 DSH，支持聊天 / 流式增量 / 审批 / 工作区 / 文件编辑 / 模型供应商。

### 4.2 它其实是一个优秀的**现成范本**

这个项目最值得学的是它的**能力与授权模型**：

| 机制 | 设计 |
|---|---|
| **Scope 模型** | `chat.read` / `chat.write` / `files.read` / `files.write` / `files.delete` / `settings.read` / `settings.write` |
| **逐设备授权** | 每台设备还需**单独的根目录授权** |
| **可撤销** | 服务端「设备」页可随时改权限或撤销设备 |
| **配对** | 配对码 **10 分钟**有效 |
| **凭据存储** | 设备令牌存 **Android Keystore** |
| **信息最小化** | 接口**不回传服务器绝对路径、不回传 API 密钥正文** |
| **国际化** | 默认中文，可切 English |

**这套模型直接建议社区 API 照抄**：

| 社区 API 的 scope | 对应的能力 |
|---|---|
| `community.read` | 读帖子 / 插件档案 |
| `community.write` | 发帖 / 评论 |
| `community.react` | 投票 / 反应 |
| `community.identity` | 读当前登录用户 |

配合「逐设备授权 + 服务端可撤销 + 配对码限时 + 凭据存 Keystore」，这是已经被验证过的安全模型。

### 4.3 我们的主动兼容：形态③（JSON API）

社区在 host 侧暴露稳定的 JSON API（见 [03](03-插件实现规格.md) 4.2）：

```
GET  /api/v1/community/plugins?q=&sort=active
GET  /api/v1/community/plugin?repo=owner/name
GET  /api/v1/community/discussions?category=&page=
GET  /api/v1/community/discussion?id=
POST /api/v1/community/discussion        （需 community.write）
POST /api/v1/community/reaction          （需 community.react）
GET  /api/v1/community/me
```

**任何原生客户端（包括但不限于 `dsh-android-app`）都能消费。** 统一错误信封 `{status, reason, message, fields, requestId}`（对齐 `dsh-workspace` 的风格），降低接入成本。

**注意**：GitHub 的 Device Flow 在原生客户端里同样可用——原生端可以直接调 `/api/v1/community/auth/start` 拿 8 位码，展示在原生 UI 里，然后轮询 `/auth/poll`。**token 始终留在 host 侧**。

## 6. 为什么不自己做一个手机端

用户已经明确「不用做手机端」，这里给出工程理由作为佐证：

1. **`dsh-android` 已经做到了「同源真 DSH + 第三方插件 ✅」**，这是最难的部分（Node 运行时 + bionic 二进制 + WebView 集成）。重做一遍没有增量价值。
2. **手机端最难的问题不是渲染，是打包 Node 运行时。** 社区插件不碰这一层。
3. **三套方案已经覆盖了三种不同的用户偏好**（完整 DSH / 轻量外壳 / 原生客户端）。再做第四套，边际价值为负。
4. **社区的核心价值在 host 侧**（多源聚合 + GitHub 桥接 + 登录）。这部分**与客户端形态无关**，做一次，三种手机端都能用。

**所以本方案的手机端策略是：把自己做成「任何客户端都能用」的服务，而不是再做一个客户端。**

## 8. 手机端相关的风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 中继不对未知路径转发 | 形态②在 `dsh-phone-pair` 内不可用 | 退路：用手机浏览器直接打开同一 URL |
| `dsh-phone-pair` 快照与运行时 DSH 版本不匹配 | 即使有 API 也可能协议不符 | 独立页面只用 `fetch` + JSON，不依赖 WebSocket/RPC 协议 |
| 插件误引原生依赖 | **在 Android 上直接崩** | CI 加一条检查：`package.json` 依赖里出现已知原生包即失败 |
| 手机弱网导致页面卡 | 体验差 | 服务端渲染首屏（形态②）+ 分层缓存 + 陈旧数据降级 |
| 中继域名变化 | 二维码失效 | 二维码在桌面端实时生成，不写死 |
