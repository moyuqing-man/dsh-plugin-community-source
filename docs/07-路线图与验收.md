# 07 · 路线图、验收与风险

> 本文件回答：**分几个里程碑？怎么算做完了？有哪些坑要先填？**

## 1. 里程碑总览

| 里程碑 | 目标 | 关键交付 | 预估 |
|---|---|---|---|
| **M0 · 可行性验证** | 验证 3 个关键假设，不写产品代码 | 一份验证报告 | 1–2 天 |
| **M1 · 保底通路** | 形态②（独立页面）+ 形态③（JSON API）跑通 | `/community` 可用，手机浏览器能打开 | 1–2 周 |
| **M2 · 身份** | Device Flow 全流程可用 | 能登录、能发帖、能评论 | 3–5 天 |
| **M3 · 桌面原生体验** | 形态①（client slot） | 侧栏入口、社区全屏页、插件详情页区块 | 1–2 周 |
| **M4 · 生态打通** | 形态④ + 多源索引 + 发布 | Agent 工具、2+ 索引源、npm 发布 | 1 周 |

**总计约 4–6 周**（单人，按 [02](02-总体架构.md) 第 6 节约 4500 行的规模估算）。

**排序原则：先保底，再优化；先手机，再桌面。**
理由：形态②是**唯一在所有环境下都可用**的通路，而且它比形态①简单（不需要构建工具链）。先把保底的做完，再回头做桌面原生体验。

## 2. M0 · 可行性验证（最重要的一步）

**这一步不写产品代码，只验证可能推翻设计的问题。** 都是可以在一两天内验证完的。

> ✅ **已经验证掉一块**：GitHub API 的能力边界已实测完成，结论见 [08](08-GitHub-API-契约.md)。
> 其中最重要的一条——**Discussions 有 REST 读接口且完全免登录**——解除了「匿名可读」这个设计支柱的风险。
> 但 [08](08-GitHub-API-契约.md) 第 10 节还剩 **POC-1、POC-3、POC-5、POC-7** 要跑（Device Flow 跑通、`createDiscussion` 亲手发帖、匿名 60/hr 真实体验、非协作者能否建帖）。**这些和下面三个假设一起做掉。**（POC-0 匿名读讨论、**POC-2 REST 无 discussions 写接口**、**POC-4 scope** —— 已由官方文档逐字确认 —— **POC-6 ETag 是否吃配额** 均已定论。POC-3 的字段级契约也已从官方文档核实，只剩亲手发帖。）

### 假设 A：非协作者能否创建 Discussion ⚠️ 最高风险

| 项 | 内容 |
|---|---|
| **假设** | 任何 GitHub 用户都能在社区自己的公开仓库里**新建 Discussion** |
| **依据** | GitHub 官方文档：「*People with read access to a repository can participate in discussions and polls in the repository.*」 |
| **为什么是风险** | 如果「create discussion」需要写权限，那「论坛」这个载体就要换，影响面最大 |
| **验证方法** | 用一个**非协作者的普通 GitHub 账号**，对社区仓库尝试「New discussion」，记录结果 |
| **如果失败** | 走 [04](04-身份与登录.md) 第 8 节的备选方案 B1（改走 Issues 写入，再同步为 Discussion） |
| **验收** | 报告里明确写「成功 / 失败」，附截图或错误信息 |

### 假设 B：`dsh-phone-pair` 的中继是否转发未知路径 ⚠️

| 项 | 内容 |
|---|---|
| **假设** | 中继域名会把 `/community` 这类**产品自带之外的路径**原样转发到电脑上的 DSH 服务 |
| **验证方法** | 在电脑上起一个自定义路由（任意 `webServer.register` 的路径），用手机通过中继域名访问该路径 |
| **如果失败** | 退路：让用户用**手机浏览器**直接打开同一 URL（浏览器没有 AssetIndex 同源闸门） |
| **验收** | 报告写明「App 内可访问 / 仅浏览器可访问」 |

### 假设 C：`dsh-phone-pair` 的构建时快照是否加载 client 插件 ⚠️

| 项 | 内容 |
|---|---|
| **假设** | **不加载**（前端是构建时快照，client 插件是运行时注入） |
| **验证方法** | 用 `dsh-android` 项目给出的字节数判据——拉取电脑端 DSH 首页 HTML，测量长度：<br>**`34846` ≈ 插件图正常；`3709` ≈ 插件图为空** | 
| **补充验证** | 在手机上通过 `dsh-phone-pair` 打开 DSH，观察一个**已装的 client 插件**（如 `dsh-workspace` 的侧栏用量摘要）是否出现 |
| **如果失败（= 插件确实加载了）** | 好消息，形态①可用；但形态②仍然要做（服务裸浏览器与原生客户端） |
| **验收** | 报告写明实测字节数与插件是否可见 |

### M0 产出物

一份 `M0-VERIFICATION.md`，含三个假设的**结论 + 证据 + 影响**。

**M0 的准出标准**：三个假设都有明确结论，且假设 A 若失败时已选定备选方案。

## 3. M1 · 保底通路

### 交付物

| # | 交付 | 验收标准 |
|---|---|---|
| 1 | 插件骨架 | `package.json` 含完整 `dsh` 字段；host 半边能被 DSH 加载；`inject` 声明正确 |
| 2 | 索引适配器（2 个源） | 至少接 `awesome-dsh-plugin` 与 `dsh-plugin-radar`，输出统一 `PluginCard` |
| 3 | GitHub 元数据层 | 能取 stars / open issues / pushed_at / archived；有 rate limit 退避 |
| 4 | 分层缓存 | 有 TTL、有陈旧数据降级（外部失败时返回旧数据 + `stale: true`） |
| 5 | `/api/v1/community/*` | 读接口全部可用，统一错误信封 |
| 6 | `/community` 独立页面 | 返回完整 HTML；**关闭 JS 也能看到帖子列表**（服务端渲染） |
| 7 | 手机可用 | 窄屏单列布局；在手机浏览器里能完整浏览 |

### 准出标准

> **在一台没有装任何 DSH 插件的手机上，用浏览器打开自定义路由地址，能看到社区帖子列表。**
>
> 这条标准把「依赖 client 插件图」这个变量彻底排除在外。

### 实现状态

**已完成**：① 插件骨架（零依赖、`lib/` 不 import 任何 `@deepseek-ai/*`，host 半边可用假 ctx 直接测）② 三个源适配器 ③ GitHub 元数据层 + 未认证配额调速器 ④ 分层缓存（TTL + 陈旧降级 + 并发去重）⑤ 读接口 + 统一错误信封 ⑥ `/community` 页面（**零前端 JS**）⑦ 窄屏单列。

**与本节原计划的偏差（记录，不隐瞒）**：

- 第 2 条原写「至少接 `awesome-dsh-plugin` 与 `dsh-plugin-radar`」，实际默认集是 **`github-topic` + `awesome`**。radar 已实现但**不进默认集**：它只有 301 条，且 `raw.githubusercontent.com` 在本机经常超时。取舍理由见 [`plugin/README.md`](../plugin/README.md)。
- 第 6 条的「帖子列表」在 M1 阶段实际呈现的是**插件列表**。真正的讨论列表要等 M2 的登录——未认证时 GitHub GraphQL 配额为 **0**，而 REST 侧根本没有 discussions 接口。M1 期间详情页会如实显示「需要登录才能读」，**而不是显示一个空列表**（把「读不到」说成「没有」，比报错更糟）。

**验收证据**：`node --test "test/*.test.mjs"` → **64 通过 0 失败**（含「30 条卡片的首页 HTML > 10000 字节」这条 DoD 断言）；`node scripts/preview.mjs` 起本地服务后，`/community` 实测返回 **24134 字节** HTML 且不含 `<script`；`/api/v1/community/plugins` 实测返回 **4500** 条索引数据。

**已知数据质量缺陷**：按 star 排序会把框架本体 `deepseek-ai/deepseek-harness`（★248k）顶到第一位——它自己也打了 `topic:dsh-plugin` 标签，而该 topic 下共有 **19055** 个仓库。GitHub 的 `topic:` 匹配是精确的（已实测验证），所以这不是查询 bug，而是「自我声明式标签」的固有问题。缓解方案（混合评分 / 可配置排除名单）待定。

## 4. M2 · 身份

| # | 交付 | 验收标准 |
|---|---|---|
| 1 | `/auth/start` | 返回 `userCode` / `verificationUri` / `expiresIn` / `interval`；**不返回 `device_code`** |
| 2 | `/auth/poll` | 正确处理 `authorization_pending` / `slow_down`（间隔 +5s）/ `expired_token` / `access_denied` |
| 3 | token 落库 | 存进 `ctx.credentials`；**插件目录下无任何 token 文件** |
| 4 | `/me` | 返回 `{ authenticated, login, avatarUrl }`；**永不返回 token** |
| 5 | 登录面板 | 大号验证码 + 复制按钮 + 打开链接 + 倒计时；可选二维码 |
| 6 | 写操作 | 发帖 / 评论 / 投票可用；未登录时按钮变为引导态 |
| 7 | 登出 | 清除凭据并回落到匿名态 |

### 准出标准

> **从零开始，到发出第一条帖子，全程不需要离开 DSH、不需要填任何表单，只输入一个 8 位验证码。**
>
> 附加检查：`grep -ri "gho_\|ghp_" <插件目录>` **无命中**。

### 实现状态

**代码已完成，测试 25 项全绿（`test/auth.test.mjs` 12 + `test/write.test.mjs` 16 中的相关项）；但「从零到发出第一帖」这条准出标准尚未实跑** —— 用户当前无法访问 GitHub，跑不了 Device Flow。

| # | 状态 | 证据 / 偏离 |
|---|---|---|
| 1 | ✅ | `test/auth.test.mjs` 断言 `start()` 与 `describeFlow()` 的返回体都不含 `device_code` |
| 2 | ✅ | 假时钟驱动：`slow_down` 后间隔从 5s 变 10s；`expired_token`→410、`access_denied`→403、`device_flow_disabled`→503 并提示勾 Enable Device Flow |
| 3 | ✅ | 走 `ctx.credentials.modifyRecord`（记录的唯一写路径），无 `credentials` 服务时降级为内存并告警；`grep` 检查在测试里断言 |
| 4 | ✅ | `/me` 只回 `{authenticated, login, configured, verificationUri, scope}` |
| 5 | ⚠️ **有意偏离** | **没有复制按钮**，改为 `user-select:all`（点一下整串选中）。原因：复制按钮要用 `navigator.clipboard`，而本项目的硬红线是**页面零前端 JS**（手机 WebView 里 client 插件图可能加载不出来，那时页面必须还活着）。二维码未做。 |
| 6 | ✅ | `POST /discussion` → 201；`POST /reaction` → 8 种枚举校验。验收用的真实发帖因无网未跑，路径已由假 HTTP 全量覆盖 |
| 7 | ✅ | 登出走 `credentials.deleteRecord` |

**额外做的三件事（原计划外）**：

1. **写操作的两道同源检查**：必须 `Content-Type: application/json` + `Origin` 同源。
   理由：不带该头就是简单请求、**不触发 CORS 预检**，恶意页面可借已登录浏览器发帖。这条是安全底线，不能等 M3 再补。
2. **幂等 + 写间隔 + POST 永不重试**：相同标题正文 60 秒内返回前一条并标 `deduped`；两次写间隔 ≥1.2 秒；`retries: 0`。对应 §8 风险清单第 12 条（重复发帖 / 被限流封 integration）。
3. **冷启动轮询本地拦截**：`poll()` 在 `now < nextPollAt` 时**不打 GitHub** 直接返回 pending。因为验证码提交上限是 **50 次/小时/应用**，全社区共用这个额度——客户端一急就把所有人一起堵死。

**一处为了正确性改掉的实现**：去重键原本用 FNV-1a 哈希。哈希撞了会出现最坏的失败模式——用户以为发出去了，实际拿到的是**上一条帖的链接**。改成完整正文做键；写入本身已被 1.2 秒间隔限住，一分钟最多 50 次，内存上界可控。

## 5. M3 · 桌面原生体验

| # | 交付 | 验收标准 |
|---|---|---|
| 1 | 侧栏入口（`sidebar.panellist`） | 点图标能切到社区页 |
| 2 | 社区主页（`main`, key=`community`） | 与形态②数据一致；跟随主题变量 |
| 3 | 插件详情区块（`plugins.detail.section`） | 在 DSH 插件详情页内可见；懒加载，不拖慢首屏 |
| 4 | 详情页标签（`plugins.detail.badge`） | 「🔥 讨论活跃」/「⚠️ 有已知坑」 |
| 5 | 设置页（`settings.section`） | 能配 client_id / owner / repo / 缓存时长 / 登出 |
| 6 | 登录浮层（`shell.overlay`） | 任意页面点登录都能弹 |

### 准出标准

> **在 DSH 的插件详情页里，不离开当前页面就能看到该插件的社区讨论与已知问题。**
>
> 这是本方案相对所有市场的**位置优势**，必须实现。

### 实现状态

代码在 `plugin/lib/client.js`（client 半边）+ `plugin/test/client.test.mjs`（9 项）+ `plugin/test/router.test.mjs` 的 M3 用例（6 项）。M3 当时全套 **116 个测试全绿**（现已增长到 153）。

| # | 交付 | 状态 | 证据 / 说明 |
|---|---|---|---|
| 1 | 侧栏入口 | ✅ | 注册 `sidebar.panellist {id:'community', order:30}`。侧栏条目的 id 与主面板 key 同名（都是 `community`）是两者自动成对的**唯一条件**，有用例锁住。 |
| 2 | 社区主页 | ✅（部分） | 注册 `main {key:'community'}`。数据走 `/api/v1/community/plugins`，与形态②同源，所以不存在两套数据。主题跟随用 `--dsw-alias-*` 变量。**「跟随主题」是靠变量继承，没有用 `ctx.theme` 做动态切换**。 |
| 3 | 详情页区块 | ✅（部分） | 注册 `plugins.detail.section {id:'community', order:40}`。**懒加载的粒度是「进入详情页才 fetch」+ AbortController 卸载中止，没有做视口级 IntersectionObserver 懒加载**。 |
| 4 | 详情页标签 | ✅（部分） | 注册 `plugins.detail.badge {id:'community', order:20}`。**没有数据时渲染 `null`**（座位规范明确要求「对自己没有内容的 subject 渲染 null」），所以匿名状态下这个标签通常不出现——这是设计，不是失效。 |
| 5 | 设置页 | ⚠️ 部分 | 注册 `settings.section {id:'community', order:45}`。**能显示** owner/repo/索引源/是否配好 clientId，能登录和登出。**「改 client_id / owner / repo / 缓存时长」没有做**——这些是 host 侧配置，改它们要写回宿主配置系统（`configEditor`），而本插件为此单开一条写通道的收益不大、风险不小。当前引导用户去改 `cordis.patch.yml`。 |
| 6 | 登录浮层 | ✅ | 注册 `shell.overlay {id:'community-login', order:70}`。未登录且已配 `clientId` 时自动出现并开始 Device Flow，成功后刷新页面。**它是自动出现的，不是「点某个按钮弹出」**：全站没有插一个统一的「登录」按钮位置（那需要占用别人的座位）。 |

**两处方法论上的偏离**：

1. **client 半边是手写的，没有构建步骤。** 本机 npm registry 不可达，装不了 esbuild/rollup；
   而且为了一个 600 行的 bundle 引入构建链，会让「clone 下来就能改」变成「先装一堆 devDependencies」。
   代价：不写 JSX，全部 `React.createElement`；没有类型检查。
2. **`/plugin` 增加了 `?pkg=` 反查。** 原计划只有 `?repo=`。实际做的时候才发现详情页的 `subject`
   只给 npm 包名（`subject.pkg.name` / `subject.row.moduleName`），没有仓库地址——不补这条，
   「不离开详情页」这条准出条件在数据层面就不成立。

**准出标准的一个诚实保留**：`/community/plugin?pkg=...` 实测能返回卡片与元数据，
但**讨论列表在未登录时读不到**（未认证 GraphQL 配额为 0，REST 没有 discussions 接口），
接口如实返回 `{available:false, reason:'TOKEN_REQUIRED'}`。
所以「不离开详情页就能看到讨论」这条**在登录态下才能完整满足**；
当前没有 token，这条只能标成「代码已就绪、待真机登录验证」。区块在未登录时显示的是
「需要登录后才能读」而不是空列表——**宁可说读不到，也不让人误以为这个插件没人讨论**。

**M4 的四个诚实的保留**

1. **英文页面上会有汉字，而且是应该有的。** 「英文串不许出现汉字」只管界面文案，不管
   `pickLocalized` 回退出来的插件描述——索引里大量条目只有中文。真机实测：
   `?lang=en` 的列表页 270 个汉字，除语言切换器里的「中文」外全部来自插件描述。
   把它当 bug 去「修」反而会把一半卡片弄成空白。

2. **新增的三个源在本机全都连不上**（2026-10-13 实测）：`dsh.works`、`dsh.lanshuagent.com`、
   `raw.githubusercontent.com`、`registry.npmjs.org`、`registry.npmmirror.com` 全部超时；
   只有 `awesome-dsh-plugin.com` 与 `api.github.com` 可达。
   所以这三个源的解析逻辑是**照上游公布的形状写的 + 离线 fixture 测的**，没有跑过真数据。
   它们标 `optIn` 就是要让「连不上」变成一个显式选择，而不是拖慢默认启动。
3. **交付 2（工具卡片自定义渲染）只走到「代码就绪」。** 渲染逻辑、注册形状、props 契约
   都有据可查（见上表），四个 client 测试也钉住了「key 必须等于 host 工具名」这件最容易
   静默出错的事；但**没有**在真实 DSH 会话里跑过一次 Agent 工具调用，所以
   「卡片在真机上长什么样、`block.content` 实际传进来的是什么形状」仍是未验证的。
   这一步需要一台能跑起工具调用、并且已装本插件的 DSH。另一个未经真机确认的点是：
   `package.json` 的 `dsh.client.inject` 里**没有**声明 `@deepseek-ai/dsh-client-ui-conversation`
   （别的插件填槽时会声明所属包）。这里与已有的 `plugins.detail.*` 两个座位保持一致——
   它们同样没有声明所属包。若真机上发现 `slots.inject` 回调不触发，第一个要试的就是把这个包名补进
   `inject`。

4. **交付 4 的「npm 公开包」这一条只走到「差一条命令」。** 已经能证明的是：
   会发布 29 个文件 / 254.0 KB、`lib/**` 的相对 import 全部落在包内（24 个文件）、
   清单必备字段齐全、运行时依赖为空。**不能**证明的是：真实 npm 的 glob 细节、
   `.npmignore` 交互、registry 端校验——这些只有 `npm pack --dry-run` 能答。
   另外 `package.json` 的 `repository` 已填好，指向**源码仓库**
   `moyuqing-man/dsh-plugin-community-source`（带 `"directory": "plugin"`，因为包在
   `plugin/` 子目录里）。仓库最终分成两个：源码 + 方案文档一个，社区仓库
   `moyuqing-man/dsh-plugin-community`（本地 `m0/community-repo/`）一个——
   `SECURITY.md` 明写「本仓库不含任何可执行代码」，分开之后这句话才是真的。
   布局与推送方式见 `plugin/PUBLISHING.md` 第 1 节。

## 7. 全局验收标准（Definition of Done）

一个功能可以交付，当且仅当**下面每一条都成立**：

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | **零原生依赖** | `package.json` 的 `dependencies` 里没有任何需要编译的包；`lib/` 下无 `.node` |
| 2 | **脱离 client 插件图可用** | 关闭 `__DSH_BOOT__` 注入（或直接用 curl）时，`/community` 仍返回完整页面 |
| 3 | **匿名可读** | 未登录状态下能看到帖子列表、帖子正文、插件档案 |
| 4 | **登录才可写** | 未登录调 `POST /discussion` 返回 401 且**不改动任何数据** |
| 5 | **token 不泄漏** | 前端网络面板里看不到 token；插件目录里搜不到；日志里搜不到 |
| 6 | **外部失败不白屏** | 断开到 GitHub 的网络后，页面显示缓存数据 + `stale` 提示，而不是报错页 |
| 7 | **插件卸载干净** | 卸载后 DOM 无残留 `<style>`、路由不再响应、无定时器 |
| 8 | **主题跟随** | 切换 DSH 明暗主题，社区页配色跟随 |
| 9 | **手机可用** | 375px 宽度下无横向滚动、无遮挡、可完成读帖与发帖 |
| 10 | **Android 不崩** | 在 `dsh-android` 上加载后，首页 HTML 长度 **> 10000 字节**（`3709` 视为失败） |

## 9. 最大的非技术风险：运营

**技术方案再漂亮，一个没人发帖的社区就是一个空页面。**

这一点必须诚实面对。可用的抓手：

| 抓手 | 做法 |
|---|---|
| **冷启动内容** | 上线前先手工把有代表性的插件的 Issues 聚合进来（形态②的只读功能就能做）。**空页面最劝退，有内容就有人停。** |
| **寄生官方讨论区** | 官方 `deepseek-ai/deepseek-harness` 已有 Discussion #3653（手机端话题）。社区上线后去那里发帖，把已有的人流引过来 |
| **让市场带流量** | 与已有多源索引**互相引用**：社区的插件详情页链回市场，README 里链回社区 |
| **低门槛第一帖** | 首页放一个「我想要」需求板的显眼入口——表达需求比写评价容易得多 |
| **插件作者的天然动力** | 作者希望有人看自己的插件。给作者一个「社区档案页 URL」可以贴到 README 里，这是零成本的推广位 |
| **不做排行榜** | 排行榜会固化头部、打击长尾，而长尾插件正是社区最有价值的部分 |

**建议**：把「社区有 10 个真实讨论」列为**上线门槛**，而不是「功能做完了就上线」。
